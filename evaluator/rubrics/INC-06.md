# Owner 私有评分细则 — INC-06

## 标准答案（Ground Truth）

- 根因：Orders 到达吞吐量超过两个 worker 的处理吞吐量，同时 KEDA 阈值和最大副本配置阻止有效扩容。
- 触发因素：订单需求窗口提高并发和到达速率。
- 促成因素：只监控 API 接受率，没有把队列深度和最老消息年龄作为完成度 SLO。

## 期望证据

- API 大多返回接受，但队列深度和最老消息年龄持续增长。
- Worker 仍 Running，处理速率低于到达速率，ScaledObject/HPA 停在两个副本。

## 可接受缓解

- 降低到达速率或恢复有效扩容，并持续验证积压和最老年龄回到健康范围。

## 常见错误假设

- HTTP 202 等于订单已经完成；Redis 完全不可用；worker Pod 崩溃。

## 纠正措施方向

- 基于年龄的 SLO、容量模型、KEDA 配置测试、积压排空预案和生产者背压。
